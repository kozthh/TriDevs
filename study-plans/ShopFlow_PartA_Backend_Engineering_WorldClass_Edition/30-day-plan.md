# ShopFlow Part A - Backend Engineering: 30-Day Study Tracker

## How to use this tracker
- Study 2 to 3 hours per day.
- Use 6 days for active study and 1 day for retrospective.
- Maintain one notes page for APIs, one for data and reliability, and one for open questions.
- Aim for one concrete deliverable each day.

## Week 1: Backend orientation

Day 1:
- Read the PDF headings and create a topic map.
- List the backend responsibilities mentioned or implied.
- Write the core question the PDF is trying to answer.

Day 2:
- Read the opening sections carefully.
- Summarize the backend’s role in the product.
- Distinguish backend work from frontend work in your own words.

Day 3:
- Capture the main backend concepts as short definitions.
- Add unfamiliar terms to a glossary.
- Write one plain-language explanation for each term.

Day 4:
- Study any examples or diagrams.
- Rewrite them as step-by-step flows.
- Note what the PDF emphasizes: clarity, separation, or reliability.

Day 5:
- Group the main ideas into categories.
- Organize your notes by APIs, services, data, and operations.
- Mark the concepts that keep repeating.

Day 6:
- Rebuild the backend topic map from memory.
- Explain the PDF’s purpose in two minutes.
- Identify the sections that need a slower second pass.

Day 7:
- Retrospective day.
- Write what feels clear and what still feels abstract.
- Pick the next section to revisit.

## Week 2: APIs and request flow

Day 8:
- Re-open the backend outline.
- Focus on request handling and API-related sections.
- Write the major decisions the PDF seems to favor.

Day 9:
- Trace a request from entry point to response.
- Write each stage as a numbered flow.
- Note where validation, routing, or transformation happens.

Day 10:
- Study service boundaries.
- Write what belongs in a service and what should stay outside.
- Capture any guidance on coupling or dependency direction.

Day 11:
- Review naming, endpoint, or contract guidance.
- Summarize the rules as short statements.
- Add one example of a good API shape and one of a bad one.

Day 12:
- Sketch a sample request-response cycle.
- Annotate errors, validation, and success states.
- Compare the sketch to the PDF.

Day 13:
- Recap API design principles from memory.
- Write a short note on what makes an API easy to use.
- List any remaining questions.

Day 14:
- Retrospective day.
- Review all request-flow notes.
- Decide what to reread before moving on.

## Week 3: Data, validation, and reliability

Day 15:
- Revisit the notes on persistence and data handling.
- Identify the reliability topics in the PDF.
- Mark anything related to consistency or integrity.

Day 16:
- Study validation rules.
- Summarize where validation should happen and why.
- Write examples of invalid input handling.

Day 17:
- Focus on error handling and failure states.
- List the failures discussed in the PDF.
- Note what the document recommends when something breaks.

Day 18:
- Review resilience, retry, timeout, or fault-tolerance ideas.
- Write each as a purpose-plus-effect pair.
- Add caution notes.

Day 19:
- Summarize maintainability practices.
- Note the design choices that make backend code easier to change.
- Highlight patterns that reduce complexity.

Day 20:
- Do a closed-book recap focused on data and reliability.
- Rebuild the reliability checklist from memory.
- Test your definitions and tradeoffs.

Day 21:
- Retrospective day.
- Write the top reliability habits you want to keep.
- Choose the weakest failure scenario to reread.

## Week 4: Applied review and synthesis

Day 22:
- Review all prior summaries.
- Identify the top backend ideas to keep permanently.
- Note repeated recommendations.

Day 23:
- Re-read the weakest sections only.
- Rewrite them in simpler language.
- Remove vague phrasing from your notes.

Day 24:
- Create a backend principles sheet.
- Include API shape, service boundaries, data handling, and reliability.
- Keep each principle short and actionable.

Day 25:
- Build one practical example using multiple ideas from the PDF.
- Describe the flow, data, and error handling.
- Record what the example teaches you.

Day 26:
- Review the entire PDF from memory first.
- Then compare your memory notes to the source.
- Correct anything inaccurate or incomplete.

Day 27:
- Write the final backend study summary.
- Include the main concepts, design rules, and biggest lessons.
- Add one action item for future practice.

Day 28:
- Run a final closed-book self-test.
- Explain the PDF from memory.
- Mark the remaining weak spots.

Day 29:
- Review the self-test results.
- Fix the mistakes in your notes.
- Write the last unresolved question.

Day 30:
- Final retrospective.
- Summarize what you learned overall.
- Decide how you will revisit the material later.
