# ShopFlow Part A - Backend Engineering (C++): Printable Checklist

## Daily Rules
- [ ] Study/code for 2 to 3 hours.
- [ ] Work 6 days.
- [ ] Use day 7 for retrospective.
- [ ] Write one short summary.
- [ ] Write one open question.

## Week 1: Backend orientation

### Day 1
- [ ] Install/verify C++ toolchain (compiler, CMake).
- [ ] Create a topic map of C++ backend responsibilities.
- [ ] Write the core question the project should answer.

### Day 2
- [ ] Read your framework's quickstart (Crow/Drogon/Pistache).
- [ ] Summarize the backend's role.
- [ ] Distinguish backend work from frontend work.

### Day 3
- [ ] Capture core concepts (RAII, smart pointers, move semantics) as definitions.
- [ ] Add unfamiliar terms to a glossary.
- [ ] Write a plain-language explanation for each.

### Day 4
- [ ] Build a minimal HTTP server with one endpoint.
- [ ] Rewrite the request lifecycle as a flow.
- [ ] Note what the framework emphasizes.

### Day 5
- [ ] Group notes into categories (routing, memory, data).
- [ ] Set up a project skeleton (src/, include/, CMakeLists.txt).
- [ ] Mark repeated concepts.

### Day 6
- [ ] Recreate the request-lifecycle diagram from memory.
- [ ] Explain the project in two minutes.
- [ ] Mark topics for a slower pass.

### Day 7
- [ ] Review the week.
- [ ] Write what is clear and what is abstract.
- [ ] Choose the next topic to revisit.

## Week 2: APIs and request flow

### Day 8
- [ ] Add 2-3 REST endpoints to the project.
- [ ] Write the major API design decisions.
- [ ] Confirm the server builds and runs.

### Day 9
- [ ] Trace a request end to end in your code.
- [ ] Write each stage as a flow.
- [ ] Note validation, routing, and JSON handling.

### Day 10
- [ ] Study service boundaries.
- [ ] Separate handler code from business-logic code.
- [ ] Capture coupling guidance.

### Day 11
- [ ] Review naming and status-code conventions.
- [ ] Summarize the rules.
- [ ] Add one good endpoint shape and one bad one.

### Day 12
- [ ] Sketch a sample request-response cycle.
- [ ] Annotate errors, validation, and success states in code.
- [ ] Compare it to your implementation.

### Day 13
- [ ] Recap API design principles from memory.
- [ ] Write what makes an API easy to use.
- [ ] List remaining questions.

### Day 14
- [ ] Retrospective day.
- [ ] Review request-flow notes and code.
- [ ] Decide what to refactor next.

## Week 3: Data, validation, and reliability

### Day 15
- [ ] Add a database driver and connect to a local DB.
- [ ] Identify reliability topics (transactions, pooling).
- [ ] Mark consistency and integrity concerns.

### Day 16
- [ ] Add input validation to handlers.
- [ ] Summarize where validation should happen.
- [ ] Write invalid-input examples with status codes.

### Day 17
- [ ] Add structured error handling (exceptions/error codes).
- [ ] List failure modes in your app.
- [ ] Note what to do when things break.

### Day 18
- [ ] Review retry, timeout, and connection-limit ideas.
- [ ] Write each as a purpose-plus-effect pair.
- [ ] Add basic timeout/retry handling somewhere.

### Day 19
- [ ] Review ownership and memory management in your code.
- [ ] Note design choices that improve changeability.
- [ ] Highlight complexity-reducing patterns (RAII, DI).

### Day 20
- [ ] Do a closed-book recap of data and reliability.
- [ ] Rebuild the reliability checklist.
- [ ] Test yourself on ownership and error-handling tradeoffs.

### Day 21
- [ ] Retrospective day.
- [ ] Write the top reliability habits.
- [ ] Choose the weakest area to revisit.

## Week 4: Applied review and synthesis

### Day 22
- [ ] Review all summaries and code.
- [ ] Identify the top C++ backend ideas.
- [ ] Note repeated recommendations.

### Day 23
- [ ] Re-code the weakest areas.
- [ ] Rewrite them more simply.
- [ ] Remove raw pointers/unclear ownership.

### Day 24
- [ ] Create a C++ backend principles sheet.
- [ ] Include API shape, boundaries, ownership, and reliability.
- [ ] Keep each principle actionable.

### Day 25
- [ ] Build a practical feature using multiple ideas.
- [ ] Describe flow, data, and error handling.
- [ ] Record what the feature teaches you.

### Day 26
- [ ] Review the project from memory first.
- [ ] Compare memory notes to the actual code.
- [ ] Correct inaccuracies.

### Day 27
- [ ] Write the final backend summary.
- [ ] Include the main rules and biggest lessons.
- [ ] Add one future practice item.

### Day 28
- [ ] Run a final closed-book self-test.
- [ ] Explain the project architecture from memory.
- [ ] Mark remaining weak spots.

### Day 29
- [ ] Review self-test results.
- [ ] Fix mistakes in notes or code.
- [ ] Write the last unresolved question.

### Day 30
- [ ] Final retrospective.
- [ ] Summarize what you learned.
- [ ] Decide how to revisit or extend the project later.
