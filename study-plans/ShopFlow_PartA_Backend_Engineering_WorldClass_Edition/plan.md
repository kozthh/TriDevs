# ShopFlow Part A - Backend Engineering

## Study Rhythm
- 6 study days per week
- 2 to 3 hours per day
- Day 7: retrospective, notes cleanup, and catch-up

## Study Method
- Read for structure first, then for implementation detail.
- Always finish a session with one written summary and one question.
- Treat the PDF as both a knowledge source and a checklist of engineering habits.

## Week 1: Backend overview and system thinking
Goal: understand the backend’s purpose, scope, and major responsibilities.

Day 1:
- Read the document headings and create a topic map.
- Note the major backend categories covered in the PDF.
- List the questions the document seems designed to answer.

Day 2:
- Read the opening sections carefully.
- Summarize what the backend is responsible for in the product.
- Write a short distinction between backend work and frontend work.

Day 3:
- Capture the main backend concepts in short definitions.
- List unfamiliar terms, architecture ideas, or tools.
- Write a plain-language explanation for each term.

Day 4:
- Study the examples or diagrams in the document.
- Rewrite each one as a flow in your own words.
- Note where the PDF emphasizes clarity, separation, or reliability.

Day 5:
- Build a glossary for backend-specific terms.
- Group terms by APIs, services, data, reliability, or workflow.
- Mark the terms that keep appearing.

Day 6:
- Recreate the topic map from memory.
- Give a 2-minute explanation of the document’s purpose.
- List the sections that need a slower second pass.

Day 7 retrospective:
- Which backend responsibilities are clear now?
- Which topics still feel too abstract?
- What example would make the ideas easier to retain?
- What should the next week concentrate on?

## Week 2: API design and request flow
Goal: understand how requests move through a backend and how APIs should be shaped.

Day 1:
- Revisit your week 1 notes before opening the PDF.
- Focus on the sections about request handling and service design.
- Identify the API-related decisions the PDF prioritizes.

Day 2:
- Trace a request from entry point to response.
- Write each step as a numbered flow.
- Note where validation, routing, or transformation happens.

Day 3:
- Study the service boundary ideas.
- Write what belongs inside a service and what should stay outside.
- Capture any guidance about coupling and dependency direction.

Day 4:
- Review any naming, endpoint, or contract guidance.
- Summarize the rules in short, reusable statements.
- Add examples of good and bad API shape if the PDF provides them.

Day 5:
- Sketch one sample backend interaction from client request to response.
- Annotate where errors, validation, and success states appear.
- Compare the sketch to the PDF guidance.

Day 6:
- Recap API design principles from memory.
- Write a short note on what makes an API easy to use.
- List any questions that still need examples.

Day 7 retrospective:
- Can I describe request flow without opening the PDF?
- What part of API design still feels uncertain?
- Which naming or boundary rule should I remember?
- What would I change in a real service after reading this?

## Week 3: Data, validation, and reliability
Goal: understand how backend systems stay correct, stable, and maintainable.

Day 1:
- Revisit the notes on persistence and data handling.
- Identify the reliability topics covered in the PDF.
- Mark anything related to consistency, durability, or integrity.

Day 2:
- Study validation rules and input safety.
- Summarize where validation should happen and why.
- Write examples of invalid input handling in plain language.

Day 3:
- Focus on error handling and failure states.
- List the types of failures the PDF discusses.
- Note what the document recommends doing when things break.

Day 4:
- Review resilience, retry, timeout, or fault-tolerance ideas.
- Write each mechanism as a purpose-plus-effect pair.
- Add any cautionary notes the PDF gives.

Day 5:
- Summarize maintainability practices from the week.
- Note the design choices that make backend code easier to change.
- Highlight any patterns that reduce complexity.

Day 6:
- Do a recall session focused on data and reliability.
- Rebuild the reliability checklist from memory.
- Test yourself on definitions and tradeoffs.

Day 7 retrospective:
- What reliability habits are now clear?
- Which failure scenarios need more attention?
- What rules should become part of my default thinking?
- What deserves a second reading next week?

## Week 4: Applied review and synthesis
Goal: turn the PDF into a reusable backend reference.

Day 1:
- Review all prior summaries.
- Identify the top 5 backend ideas you want to keep.
- Note any repeated recommendations across sections.

Day 2:
- Re-read the weakest sections only.
- Rewrite them in simpler language.
- Remove vague phrasing from your notes.

Day 3:
- Create a backend principles sheet.
- Include API shape, service boundaries, data handling, and reliability.
- Keep each principle short and actionable.

Day 4:
- Build one practical example that uses multiple ideas from the PDF.
- Describe the flow, data, and error handling in the example.
- Record what the example teaches you.

Day 5:
- Review the entire PDF from memory first.
- Then compare your memory notes to the source.
- Correct anything inaccurate or incomplete.

Day 6:
- Write a final backend study summary.
- Include the main concepts, the design rules, and the biggest lessons.
- Add one action item for future practice.

Day 7 retrospective:
- Which backend ideas now feel practical rather than theoretical?
- Which notes should be kept as a reference sheet?
- What topic should be repeated before moving on?
- What will I do differently in the next study cycle?
